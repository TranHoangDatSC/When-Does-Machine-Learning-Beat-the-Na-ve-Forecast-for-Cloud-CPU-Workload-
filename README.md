# Does machine learning beat the naive forecast for cloud CPU workload?

*English below is the primary text. Bản tiếng Việt ở nửa dưới.*

This repository holds everything needed to reproduce a study of short-horizon CPU
workload forecasting for cloud virtual machines. The study asks how much the answer to
*"does a machine-learning model beat the naive forecast?"* depends on choices that papers
usually leave implicit: the error metric, the training loss, the normalisation, and the
filter used to decide which machines enter the population.

Everything here is reproducible from raw public traces. The design was frozen before the
confirmation runs; the frozen text is kept verbatim, and every later departure from it is
recorded rather than quietly edited away.

---

## What the study asks

| | Question | Experiment |
|---|---|---|
| RQ1 | How much does the conclusion *"the model beats the naive forecast"* change when the normalisation, the loss function and the evaluation metric change, across three forecast horizons? | A |
| RQ2 | Does the RQ1 conclusion hold across different time periods? | B |
| RQ3 | How well does a model trained on one trace transfer to another? | C |

Supplementary analyses: synthetic aggregated machines, a no-interpolation control,
sensitivity to the population filter threshold, a narrow-scope Random Forest, and an
asymmetric cost scenario.

Three environments are used: two Bitbrains traces (fastStorage and Rnd) and one Alibaba
cluster trace, at 5-minute resolution, with forecast horizons of 1, 6 and 12 steps
(5 minutes, 30 minutes, 1 hour).

## What is in this repository

| Path | Contents |
|---|---|
| `PROTOCOL.md` | The experimental design, plus dated records of every departure from it; Appendix C holds the design as frozen on 23 Sep 2026, verbatim |
| `src/cwp/` | Library: preprocessing, feature matrix, splits, models, metrics |
| `scripts/` | One script per pipeline stage, plus the orchestrator `dieu_phoi.py` |
| `tests/` | 56 unit tests covering the checks that guard the results |
| `config/` | Dataset declarations, split boundaries, preprocessing and feature settings |
| `ket_qua_tham_chieu/` | Result tables from our full run, for comparison |
| `notebooks/colab_gru.ipynb` | The GRU stage, which needs a GPU |

Raw data and per-row predictions are **not** in the repository: the raw traces are about
11 GB and the predictions about 2 GB. Both are regenerated by the pipeline.

The code and its comments are written in Vietnamese. This README and the run instructions
are bilingual.

## Requirements

```bash

```

## Getting the raw data

Download the two public traces and place them exactly as follows:

```text
data/raw/Bitbrains-fastStorage/08-2013/*.csv        GWA-T-12 Bitbrains, fastStorage (1,250 VMs)
data/raw/Bitbrains-Rnd/2013-7/*.csv                 GWA-T-12 Bitbrains, Rnd, July 2013 (500 VMs)
data/raw/Bitbrains-Rnd/2013-8/*.csv                 GWA-T-12 Bitbrains, Rnd, August 2013 (500 VMs)
data/raw/Bitbrains-Rnd/2013-9/*.csv                 GWA-T-12 Bitbrains, Rnd, September 2013 (500 VMs)
data/raw/Alibaba-Cluster-Trace/machine_usage.csv    Alibaba cluster trace v2018, machine_usage table
```

- Bitbrains: Grid Workloads Archive, GWA-T-12 (TU Delft) —
  <http://gwa.ewi.tudelft.nl/datasets/gwa-t-12-bitbrains>
- Alibaba: <https://github.com/alibaba/clusterdata/tree/master/cluster-trace-v2018>

Which 500 Alibaba machines are used is fixed in `config/e3_machines.txt`, so the sample
does not depend on when you run it. Experiment B needs all three Rnd months; Experiment A
alone needs only August.

`data/README.md` has the file formats, the sizes of everything the pipeline builds, and how
to point `data/raw` at a copy you already have instead of downloading 11 GB again.

## Running the pipeline

`scripts/dieu_phoi.py` lists every stage with its measured runtime and its dependencies:

```bash
python scripts/dieu_phoi.py --liet-ke      # list all stages
python scripts/dieu_phoi.py --chay K2      # run one block
python scripts/dieu_phoi.py --trang-thai   # what has finished
```

Stages must run in order, because each consumes what the previous one produced. The
longest are K4.1 (28.9 h) and K6.3 (8.7 h). Blocks K4 and later can also be launched
directly as ordinary commands; the orchestrator prints the exact command for each.

The GRU stage is split in two because it needs a GPU: `K8.1` exports a data package, you
run `notebooks/colab_gru.ipynb` on Colab, and `K8.2` imports the results back after five
integrity checks.

## Three ways to check our numbers, at three costs

This is the point of the repository. You choose how much machine time to spend; each level
checks strictly more than the one above it.

### Level 1 — read our tables (no data, no run, seconds)

`ket_qua_tham_chieu/` holds every aggregated table from our full run: per-combination
metrics, hypothesis tests, transfer ratios, row counts, the chosen hyper-parameters, and
the full cross-validation log. Every number in the paper comes from these files. Nothing
here needs raw data.

```bash
python -m unittest discover -s tests       # 56 tests, about 15 seconds
```

The tests exercise the checking logic itself — the row-set intersection rule, the
float tolerance, the deduplication of the CV log, the family-reference rule — on synthetic
data, so they run without downloading anything.

### Level 2 — rebuild the data only (about 30 minutes)

Download the raw traces, then run the data-building blocks and check what you built against
what we built:

```bash
python scripts/dieu_phoi.py --chay K1
python scripts/dieu_phoi.py --chay K2
python scripts/dieu_phoi.py --chay K3
python scripts/van_tay_du_lieu.py
```

`van_tay_du_lieu.py` compares your `data/` against a content fingerprint of ours, column by
column. It is deliberately insensitive to parquet encoding, compression and library
version, because those change the bytes of a file without changing the data. If this
passes, every later stage on your machine starts from exactly the inputs ours did.

This level catches the failure mode that matters most: a preprocessing step that silently
produces different rows.

### Level 3 — run everything (about 47 hours)

Run the blocks in order, then compare every table:

```bash
python scripts/dieu_phoi.py --liet-ke      # the full order, with measured runtimes
python scripts/doi_chieu_tham_chieu.py
```

`doi_chieu_tham_chieu.py` compares each table in `ket_qua_tham_chieu/` against the table at
the same path under `results/`, cell by cell, and exits non-zero on any difference beyond
`1e-9`. It reads only; it never writes. **A partial run is fine** — stages you have not run
are reported as missing rather than as mismatches, so you can stop after any block and
check what you have.

At this level you can also re-derive the consistency properties directly from the per-row
predictions, which no table can fake:

```bash
python scripts/kiem_ket_qua.py --thi-nghiem tat-ca
```

It checks eleven properties: that every comparison family scored on exactly the same rows,
that no prediction inside the scored set is missing or infinite, that the ground truth
stored beside each prediction matches the preprocessed data, that baseline models give
identical predictions under both normalisations, and that the pre-declared grid of
combinations has no missing cell.

### Do the two paths agree?

They must, and the comparison script is how you find out. Two caveats, stated plainly.

Aggregated tables are compared numerically with a `1e-9` tolerance rather than byte for
byte, because a few statistics pass through a bootstrap and may differ in the last digit
between runs. Every difference that could change a conclusion is far larger than that
tolerance.

Intermediate parquet files are compared by **content**, not by bytes. Two machines running
pinned library versions usually produce byte-identical files — we rebuilt several and got
exactly that — but a different pyarrow build can lay out the same data differently. The
fingerprint reports byte differences separately from content differences, and only content
differences mean your data is not ours.

## Honesty notes

Two departures from the frozen design were found while running, and both are recorded in
full rather than corrected after the fact:

- **D1** (`PROTOCOL.md`, Appendix A): the hyper-parameter grid for XGBoost that actually
  ran had three candidates, not the two the frozen design specifies. The extra candidate
  was selected in 7 of 36 cases. The test set played no part in that selection.
- **D2** (`PROTOCOL.md`, Appendix B): for Experiment B the bootstrap resamples by machine,
  although the design calls for resampling by day block. This affects only the confidence
  interval of the median ratio, not the point estimates or the hypothesis tests.

`PROTOCOL.md` also carries a dated log of everything clarified after the freeze. No
experiment was ever re-run to obtain a better number, and no design choice was changed
after seeing results.

One directory needs a word of warning: `ket_qua_tham_chieu/tn_b_thu/` holds a trial run on
development data, used only to measure cost before the confirmation runs. Its numbers are
not part of any result and must not be reported.

# Học máy có vượt được dự báo naive cho tải CPU trên đám mây không?

Kho mã này chứa đủ mọi thứ để dựng lại một nghiên cứu về dự báo tải CPU ngắn hạn cho máy
ảo đám mây. Nghiên cứu hỏi: câu trả lời cho *"có mô hình học máy nào vượt được dự báo
naive không?"* phụ thuộc bao nhiêu vào những lựa chọn mà các bài báo thường để ngầm — tiêu
chí đánh giá, hàm mất mát khi huấn luyện, cách chuẩn hoá, và ngưỡng lọc quyết định máy nào
được vào quần thể.

Mọi thứ ở đây dựng lại được từ dữ liệu công khai. Thiết kế được khoá trước lượt chạy xác
nhận; bản khoá giữ nguyên văn, và mọi sai lệch về sau đều được ghi lại chứ không sửa lặng.

## Nghiên cứu hỏi gì

| | Câu hỏi | Thí nghiệm |
|---|---|---|
| RQ1 | Kết luận *"mô hình vượt dự báo naive"* thay đổi bao nhiêu khi đổi chuẩn hoá, hàm mất mát và tiêu chí đánh giá, ở ba tầm dự báo? | A |
| RQ2 | Kết luận của RQ1 có giữ nguyên qua các giai đoạn thời gian khác nhau không? | B |
| RQ3 | Mô hình học ở một tập vết dùng lại được ở tập vết khác đến mức nào? | C |

Phân tích bổ sung: máy giả ghép nhóm, đối chứng không nội suy, độ nhạy ngưỡng lọc quần
thể, Random Forest phạm vi hẹp, và kịch bản chi phí bất đối xứng.

Ba môi trường: hai tập vết Bitbrains (fastStorage và Rnd) và một tập vết cụm Alibaba, lưới
5 phút, tầm dự báo 1, 6 và 12 bước (5 phút, 30 phút, 1 giờ).

## Trong kho mã có gì

| Đường dẫn | Nội dung |
|---|---|
| `PROTOCOL.md` | Thiết kế thực nghiệm, kèm ghi nhận theo ngày về mọi sai lệch; Phụ lục C giữ nguyên văn thiết kế đúng lúc khoá ngày 23/09/2026 |

| `tests/` | 56 kiểm thử cho các phép kiểm bảo vệ kết quả |
| `config/` | Khai báo dữ liệu, ranh giới chia, cấu hình tiền xử lý và đặc trưng |

Dữ liệu thô và dự đoán từng dòng **không** nằm trong kho mã: dữ liệu thô khoảng 11 GB, dự

## Ba mức kiểm chứng, ba mức chi phí

Đây là mục đích chính của kho mã. Bạn chọn bỏ ra bao nhiêu thời gian máy; mức sau kiểm
được nhiều hơn hẳn mức trước.

`ket_qua_tham_chieu/` chứa mọi bảng gộp của lượt chạy đầy đủ: chỉ số theo từng tổ hợp, kiểm

Mọi con số trong bài đều lấy từ những tệp này.

```bash
python -m unittest discover -s tests       # 56 kiểm thử, khoảng 15 giây
```

Các kiểm thử chạy trên dữ liệu tổng hợp nên không cần tải gì: chúng kiểm chính phần logic
bảo vệ kết quả — luật lấy giao tập dòng, dung sai số thực, việc khử trùng nhật ký dò chéo,

### Mức 2 — dựng lại dữ liệu (khoảng 30 phút)

Tải dữ liệu thô, chạy các khối dựng dữ liệu, rồi đối chiếu thứ bạn dựng với thứ chúng tôi

`van_tay_du_lieu.py` so `data/` của bạn với vân tay nội dung của chúng tôi, theo từng cột.
Nó cố ý không nhạy với cách nén, cách chia row-group và phiên bản thư viện parquet, vì
những thứ đó đổi byte của tệp mà không đổi dữ liệu. Qua được mức này nghĩa là mọi bước sau
trên máy bạn khởi đầu từ đúng đầu vào của chúng tôi.

Mức này bắt được kiểu hỏng đáng sợ nhất: một bước tiền xử lý lặng lẽ cho ra tập dòng khác.

### Mức 3 — chạy hết (khoảng 47 giờ)

`doi_chieu_tham_chieu.py` so từng ô của mọi bảng trong `ket_qua_tham_chieu/` với bảng cùng

bạn dừng ở khối nào cũng kiểm được phần đã có.

Ở mức này bạn còn dựng lại được các tính chất nhất quán thẳng từ dự đoán từng dòng, thứ mà
không bảng tổng hợp nào giả được:

```bash

```

Nó kiểm mười một tính chất: mọi họ so sánh chấm trên đúng cùng một tập dòng, không dòng nào
trong tập chấm bị thiếu hay vô hạn, giá trị thật lưu cạnh mỗi dự đoán khớp dữ liệu đã tiền
xử lý, mô hình cơ sở cho dự đoán y hệt nhau ở hai chế độ chuẩn hoá, và lưới tổ hợp đã chốt
không thiếu ô nào.

### Hai đường có cho cùng kết quả không?

Phải cho cùng kết quả, và script đối chiếu là cách bạn biết điều đó. Hai điểm cần nói thẳng.

Bảng gộp được so bằng số với dung sai `1e-9` chứ không so từng byte, vì vài thống kê đi qua
bootstrap nên có thể lệch ở chữ số cuối giữa hai lần chạy. Mọi khác biệt đủ sức đổi một kết
luận đều lớn hơn dung sai đó rất nhiều.

Tệp parquet trung gian được so theo **nội dung**, không theo byte. Hai máy dùng đúng phiên
bản thư viện đã ghim thường cho ra tệp trùng từng byte — chúng tôi đã dựng lại vài tệp và
đúng như vậy — nhưng một bản pyarrow khác có thể sắp xếp cùng dữ liệu theo cách khác. Vân
tay báo riêng khác biệt byte và khác biệt nội dung; chỉ khác biệt nội dung mới có nghĩa là
dữ liệu của bạn không phải dữ liệu của chúng tôi.

## Những điều cần nói thẳng

Hai sai lệch so với thiết kế đã khoá được phát hiện trong lúc chạy, và cả hai đều được ghi
đầy đủ thay vì sửa lại cho đẹp:

- **D1** (`PROTOCOL.md`, Phụ lục A): lưới siêu tham số của XGBoost thực sự chạy có ba ứng
  viên chứ không phải hai như thiết kế đã khoá. Ứng viên thêm được chọn ở 7 trong 36 trường
  hợp. Tập test không tham gia vào việc chọn đó.
- **D2** (`PROTOCOL.md`, Phụ lục B): với Thí nghiệm B, bootstrap lấy mẫu lại theo máy trong
  khi thiết kế quy định lấy mẫu lại theo khối ngày. Điều này chỉ ảnh hưởng khoảng tin cậy
  của tỉ số trung vị, không ảnh hưởng ước lượng điểm hay kiểm định.

`PROTOCOL.md` còn có nhật ký theo ngày của mọi chỗ được làm rõ sau khi khoá. Không thí
nghiệm nào được chạy lại để lấy con số đẹp hơn, và không lựa chọn thiết kế nào bị đổi sau
khi đã thấy kết quả.

Một thư mục cần lưu ý: `ket_qua_tham_chieu/tn_b_thu/` là lượt chạy thử trên dữ liệu phát
triển, chỉ dùng để đo chi phí trước lượt xác nhận. Số của nó không thuộc kết quả nào và
không được đem báo cáo.
